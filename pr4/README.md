# Практична робота №4: Керування контекстом і Structured Output

Цей проєкт перетворює помічника служби підтримки інтернет-магазину «Сузірʼя» на діалогового AI-асистента з гарантованим structured output, програмною валідацією контракту, динамічним керуванням контекстом і бюджетом токенів.

## 2. Швидкий старт

### Підготовка віртуального середовища
```bash
python -m venv .venv
.\.venv\Scripts\Activate.ps1   # для Windows PowerShell
# source .venv/bin/activate    # для Linux / macOS
pip install -r requirements.txt
```

### Налаштування `.env`
Створіть файл `.env` (скопіювавши з `.env.example` або використавши налаштування з ПР3):
```env
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_API_KEY=ваш_ключ_з_google_ai_studio
LLM_MODEL=gemini-3.1-flash-lite
LLM_TEMPERATURE=0.2
LLM_MAX_TOKENS=800
LLM_TIMEOUT=30
LLM_TOKEN_BUDGET=3000
```

### Перевірка середовища
```bash
python check_env.py
```
Скрипт перевіряє сумісність Python, наявність пакетів, валідність `.env` та робить тестовий запит зі схемою відповіді.

### Запуск веб-застосунку
```bash
uvicorn app.main:app --reload
```
Відкрийте у браузері: [http://127.0.0.1:8000](http://127.0.0.1:8000).

## 3. Як працюють ключові механізми та обґрунтування рішень

### 3.1. Робота з `context.md` (Джерело істини)
* **Принцип:** Правила магазину не зашиті в Python-код, а динамічно зчитуються з файлу [`context.md`](file:///C:/Застосунки_З_ШІ/pr4/context.md) під час кожного запиту.
* **Чому це важливо:** Будь-яка зміна умов доставки, гарантії чи способів оплати в `context.md` миттєво змінює поведінку асистента без перезапуску сервера чи редагування коду.
* **Довірений контекст:** Текст із `context.md` передається як відокремлене системне повідомлення з поміткою «єдине офіційне джерело правил».

### 3.2. Structured Output та JSON Schema ([`app/schema.py`](file:///C:/Застосунки_З_ШІ/pr4/app/schema.py))
* **Контракт [`AssistantResponse`](file:///C:/Застосунки_З_ШІ/pr4/app/schema.py):**
  1. `reply` (`str`) — текст відповіді, що безпосередньо показується користувачеві.
  2. `topic` (`TopicEnum`) — категорія звернення з фіксованого переліку (`order`, `delivery`, `payment`, `return`, `warranty`, `support`, `other`).
  3. `based_on_rules` (`bool`) — чи відповідь ґрунтується на правилах з `context.md`.
  4. `needs_clarification` (`bool`) — прапорець, що сигналізує про необхідність уточнення у клієнта.
  5. `transfer_to_operator` (`bool`) — потреба переведення розмови на людину-оператора.
  6. `order_number` (`Optional[str]`) — 6-значний номер замовлення (якщо звучав у діалозі).
* **Чому `topic` є `enum`:** Фіксований перелік запобігає «творчості» моделі (наприклад, створенню випадкових тем на зразок `complaint_about_delay`), що критично для автоматичної маршрутизації тікетів у CRM/Helpdesk.
* **Чому `extra="forbid"`:** Заборона непередбачених полів гарантує стабільність контракту.
* **Що гарантує `response_format`, а що перевіряє Python:**
  * `response_format` гарантує синтаксичну структуру JSON на рівні декодера LLM.
  * Проте модель може згенерувати невалідні дані або обірватися при таймауті. Функція [`validate`](file:///C:/Застосунки_З_ШІ/pr4/app/schema.py) на стороні Python:
    - очищає можливі markdown-огорожі (```json ... ```);
    - проводить валідацію через Pydantic;
    - додатково верифікує регулярним виразом `^\d{6}$` форму номера замовлення.
* **Важливе застереження про `based_on_rules`:** Поле `based_on_rules` є суб'єктивним твердженням самої моделі. JSON Schema гарантує тип `bool`, але НЕ гарантує правдивість. Це було наочно доведено у бенчмарку, де Config 2 без правил ставив `based_on_rules=true` на галюцинаціях.

### 3.3. Керування історією та надійність діалогу
* **Що зберігається в історії:** В історії зберігаються репліки клієнта та **виключно текст відповіді помічника (`reply`)**, а не весь технічний JSON.
  * *Обґрунтування:* Технічні службові поля (`topic`, `transfer_to_operator`, метадані) займають зайві 100+ токенів на кожну відповідь. Збереження лише `reply` заощаджує до 65% контексту, дозволяючи вести втричі довший діалог.
* **Довіра до історії клієнта:** Клієнт надсилає історію з фронтенду, що робить бекенд stateless. Проте сервер виконує **санітизацію** ([`sanitize_history`](file:///C:/Застосунки_З_ШІ/pr4/app/llm.py)):
  - фільтруються недозволені ролі (дозволені тільки `user` та `assistant`);
  - обмежується максимальна довжина окремої репліки (до 2000 символів), щоб унеможливити атаки вичерпання контексту.

### 3.4. Бюджет токенів та правило скорочення ([`app/llm.py`](file:///C:/Застосунки_З_ШІ/pr4/app/llm.py))
* **Бюджет `LLM_TOKEN_BUDGET` (3000 токенів):**
  1. Системна інструкція, правила `context.md` та поточне повідомлення клієнта є **недоторканними** (вони гарантують роль, достовірність і розуміння свіжого запиту).
  2. Резервується бюджет на генерацію відповіді (`RESERVED_COMPLETION_TOKENS = 600`).
  3. Решта токенів виділяється під історію діалогу.
* **Правило скорочення (FIFO):**
  Функція [`fit_budget`](file:///C:/Застосунки_З_ШІ/pr4/app/llm.py) відбирає повідомлення з кінця (від найновіших до найстаріших). Якщо історія розростається, найстаріші повідомлення витісняються першими, зберігаючи актуальний контекст останніх повідомлень.
* **Оцінка токенів ([`estimate_tokens`](file:///C:/Застосунки_З_ШІ/pr4/app/llm.py)):**
  Використовується калібрована евристика для української мови `ceil(len(text) / 2.9) + 4`. На практиці розбіжність між оцінкою бекенду та фактичним `prompt_tokens` становить менше 3%.

### 3.5. Обробка збоїв та Retry-логіка
* **Збої API (перенесені з ПР3):**
  - `AuthenticationError` (401) — невірний API-ключ.
  - `APITimeoutError` (504) — вичерпано таймаут очікування.
  - `APIStatusError` 429 — перевищення Rate Limit.
  - `APIConnectionError` (503) — збій мережі / недоступність сервісу.
* **Обробка невалідної відповіді моделі:**
  Якщо відповідь не проходить [`schema.validate()`](file:///C:/Застосунки_З_ШІ/pr4/app/schema.py), система виконує **максимум 1 повторний запит (retry)**, передаючи моделі отриману відповідь та опис помилки схеми. Якщо повторна спроба також не пройшла валідацію, клієнту повертається безпечна помилка HTTP 502, а технічні деталі фіксуються в логах. Нескінченні цикли виключені.

## 4. Порівняння конфігурацій та результати

Для запуску порівняльного дослідження:
```bash
python compare/run_compare.py
```

### Підсумки тестування (39 запусків на 7 зверненнях та 2 діалогах):
* **Config 1 (Fuzzy baseline):** 0% валідних схем, численні галюцинації (вигадування доставки до Польщі, хибних умов повернення), підкорення prompt injection.
* **Config 2 (Structured prompt без правил):** 100% валідних JSON, але 5 фактичних помилок через відсутність `context.md` (модель самовпевнено ставила `based_on_rules=true` на власних вигадках) та 0% пам'яті в діалогах.
* **Config 3 (Context Engineering):** **100% валідна схема, 100% пам'ять номерів замовлень у діалогах, 0 фактичних помилок**.

Повний звіт з матрицею класифікації помилок та аналізом latency/токенів дивіться у [`compare/README.md`](file:///C:/Застосунки_З_ШІ/pr4/compare/README.md).
